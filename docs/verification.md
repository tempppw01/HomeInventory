# 验证覆盖地图

这份文档回答两个问题:**现在有哪些自动化检查**、以及**哪些地方其实没被覆盖**。
后一半更重要 —— 一份只列「我们测了什么」的清单容易让人误以为「都测过了」。

> 数字会随提交变化;下表以 v0.1.3 之后的 `76d667c` 为准(本地跑出的条数)。

## 检查的写法原则

这几条是从实际踩坑里得出来的,新加检查时一并遵守:

1. **修产品,不修改检查**。检查报错时先问「产品是不是真的错了」;确认是检查写错才改检查
   (这段时间里两种都发生过,也都记录在提交信息里)。
2. **每条新检查都要能失败**。加完检查后,故意注入一次错误、确认它变红,再撤回。
   不能失败的检查等于没有检查。
3. **不许空跑**。断言前要确认「确实取到了数据」:没有可比对的文字、没记录到网络请求、
   统计到 0 个元素,都判为失败而不是通过。
4. **先怀疑测量,再怀疑产品**。颜色按 `rgb()` 解析但浏览器给的是 `oklch()`、
   主题过渡动画的中间态、嵌套弹窗的层级判断 —— 这几次「假失败」最后都出在测量方式上。
5. **数据状态要进种子**。只测「健康状态」的数据会让一大批界面元素永远测不到
   (见下文「按数据状态」一节)。
6. **「写了」不等于「跑了」**。配置类的东西(全局闸门、中间件、代理)必须有一条**静态**检查,
   确认它在框架真正会加载的位置。`middleware.ts` 放在仓库根目录、而项目是 `src/app` 布局时,
   Next 会**静默忽略**它 —— 构建产物里一条都没编出来,而当时所有用例照样全绿。
   现在由 `verify-write-guards` 守着这一条。

## 一、纯函数单测(`npm run test:unit`)

| 模块 | 覆盖要点 |
| --- | --- |
| `validation` / 日期 | 两种合法写法、非法值与不存在的日期、时间点字段保留时刻 |
| `low-stock` / `expiry-status` | 该补货的两种触发、暂停期、今天到期算临期而非过期 |
| `item-forecast` | 消耗速度学习、重复分组(含「一方包含另一方」) |
| `item-merge` / `item-metrics` / `item-sort` / `item-insight` | 合并计划、单位换算、排序、结论文字 |
| `household-report` / `space-summary` / `chart` / `spend-forecast` | 月报数字、空间摘要、图表聚合 |
| `csv-import` / `item-type-guess` / `fridge` / `task-recurrence` | 导入解析、类型猜测、冷藏规则、重复任务的下一次到期 |
| `password` / `validation`(账号) | 密码强度各档、用户名规则 |
| `local-date` / `weekly-review` / `relative-time` | 本地日历日、每周盘点设定日、相对时间文案 |
| `interactive-nesting` | 「行里的 trailing 是不是控件」的判定(判断错了就会渲染出 `<button>` 套 `<button>`) |
| `ai-error` | 上游 AI 报错的解读:各状态码与两种「图片链接被拒」措辞、HTML 去标签、超长截断;外加一条源码级守卫 —— 四个 AI 路由里不许再自己拼失败文案 |
| 一致性 | 服务端写入的动作都有中文标签;代码引用的 `/api` 路径都有对应路由 |
| 写接口守卫 | 每个非 GET 处理器必须有权限校验,或在「设计上公开 / 自带细粒度校验」清单里(清单同时校验不过期) |
| 配置文档一致性 | 代码用到的用户可配置环境变量都必须在 README / compose 里出现;开发专用白名单同时校验不过期 |
| CI 工作流自检 | 每个步骤有 run/uses、引用的脚本存在、关键作业与检查仍在(工作流无效时 CI 根本不会跑,所以这条放在本地 test:unit 最前) |
| 两份 schema 同步 | MySQL 用的 `schema.mysql.prisma` 必须与 `schema.prisma` 的表/字段完全一致(容器启动时会用它覆盖正式 schema) |

**300 条**(最近一次全绿)。`npm run test:unit` 会通过 `scripts/lib/register-alias.mjs` 注册 `@/` 别名解析,
以便直接测引用了其他模块的文件。

## 四、发布前

镜像构建流程里带一次**运行时冒烟**:容器起来后完成
「初始化管理员 → 登录 → 建物品 → 读回」,两个架构各跑一次(arm64 在原生 runner 上单独再跑一次)。

## 五、按数据状态看覆盖

界面检查能测到什么,取决于**库里有什么数据**。CI 的种子数据(`scripts/seed-ci-fixtures.mjs`)
专门覆盖「只有特定状态才会出现」的元素:

| 状态 | 种子数据里有什么 | 影响哪些界面元素 |
| --- | --- | --- |
| 已过期 | 3 天前到期的酸奶 | 红色到期徽标、概览红点、提醒中心过期分组 |
| 即将到期 | 5 天后到期的鲜奶 | 提醒中心临期行 |
| 低库存 | 最小库存 5 / 数量 1 | 该补货角标、补货建议 |
| 余量见底 | 清洁瓶装 8% | 液体余量徽标 |
| AI 结论过时 | 带 `aiSummary` + 旧 `AI_ANALYZE` 记录 | 列表「建议重新分析」胶囊 |
| 回收站有东西 | 一件已软删 | 回收站弹窗的行 |
| 采购 / 任务非空 | 一条待采购、一条任务 | 两个视图的行 |

> 这张表是**补出来的**:此前种子里只有健康状态的物品,上面这些元素在 CI 里从未被对比度、
> 窄屏、无障碍检查看到。补上之后第一次运行就抓到「建议重新分析」在深色下对比度只有 2.03。

> 并发也算一种「数据状态」:同一份数据被多个写者同时改。相关检查见 `verify-concurrency`。

> 另外:`/consume/[id]` 是**无需登录**的写入口(扫码即消耗一件),
> 它的幂等与液体分支由 `verify-consume-scan` 覆盖。

## 六、已知未覆盖(诚实清单)

| 方向 | 为什么没做 |
| --- | --- |
| 首屏渲染时间(LCP/TTI) | 机器相关,进 CI 只会产生假失败;体积预算与相对耗时阈值已覆盖可稳定比较的部分 |
| 对象存储(OSS)上传 | 需要真实 OSS 配置;而**默认的本地存储路径**已由 `verify-image-upload` 覆盖(上传→落盘→读回→删除清理) |
| AI 相关功能 | 需要 API Key(gated by `aiAvailable`);套件在未配置时打印跳过原因而不是伪装通过 |
| 相机 / 屏幕共享扫码 | 需要真实摄像头与屏幕共享权限;但**解码链路**已由 `verify-qr-scan` 覆盖(用应用自己生成的二维码走「图片」模式) |
| 纸上的最终结果 | 排版几何(尺寸/边界/换行)已用 print 媒体验过,但真实打印机的输出无法在 CI 里验证 |
| 两个标签页同时操作 | v0.1.30 手工探针确认行为正确:一处删掉、另一处正在编辑并保存时会明确报「找不到这条记录,可能已被删除」,且不关掉弹窗把用户的改动丢掉。但**没有**写成回归:驱动「另一处删除」需要在同一 context 开第二个标签页并在恰当时机操作,叠上自动弹层后不稳定 |
| 请求发不出去(断网 / 接口失败) | 手工探针确认会提示「网络响应不完整,请重试;已保存的内容不会丢失」且服务端数据不变;但没能做成稳定可复现的自动检查(Playwright route abort 在有 Service Worker 时不生效,屏蔽 SW 后又常被自动弹层遮挡;「用掉」路径先弹应用内确认框、请求时机不稳)。按「做不稳的检查不写进去」的原则留空 |
| 空间卡片的右键菜单(自动化) | 删空间这条路径的唯一入口是卡片右键菜单;实测 Playwright 右键、按坐标右键、直接派发 contextmenu 都打不开菜单(三次),所以「删空间」的**界面级**断言没有写成回归。文案逻辑已抽成纯函数 `spaceDeletePrompt`,由 `scripts/unit/space-delete-prompt.test.mjs` 覆盖 |
| 打印工作室的自动扫描 | 它是嵌套弹窗,自动判定不稳定,所以没有纳入**弹窗扫描**(在 `verify-modals-a11y` 里写明了原因)。但它的**内容**已有覆盖:v0.1.29 起 `verify-print-layout` 会自建一件 49 字的探针物品,量标签上的名字是否真的显示两行、超出行钳、二维码是否够扫、编号是否印出来 |

## 七、怎么跑

```bash
npm run test:unit                      # 纯函数单测(不需要服务)
npm run build && PORT=3001 npm start   # 起本地生产服务
node scripts/seed-ci-fixtures.mjs      # 需要时播种「只有特定状态才出现」的数据

PROBE_USER=bgs PROBE_PASS=... node scripts/verify-entry-fixes.mjs
PROBE_USER=bgs PROBE_PASS=... PROBE_VIEWER_PASS=... node scripts/verify-contrast.mjs
```

只读角色相关的检查需要 `PROBE_VIEWER_PASS`;探针账号由
`node scripts/make-probe-accounts.mjs` 创建(CI 里每个界面作业都会先跑)。
