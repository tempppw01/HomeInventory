# 验证覆盖地图

这份文档回答两个问题:**现在有哪些自动化检查**、以及**哪些地方其实没被覆盖**。
后一半更重要 —— 一份只列「我们测了什么」的清单容易让人误以为「都测过了」。

> 数字会随提交变化;下表以 v0.1.3 之后的 `76d667c` 为准(本地跑出的条数)。

## 检查的写法原则

这几条是从实际踩坑里得出来的,新加检查时一并遵守:

1. **修产品,不修改检查**。检查报错时先问「产品是不是真的错了」;确认是检查写错才改检查
   (这段时间里两种都发生过,也都记录在提交信息里)。
2. **每条新检查都要能失败**。加完检查后,故意注入一次错误、确认它变红,再撤回。
   不能失败的检查等于没有检查。
3. **不许空跑**。断言前要确认「确实取到了数据」:没有可比对的文字、没记录到网络请求、
   统计到 0 个元素,都判为失败而不是通过。
4. **先怀疑测量,再怀疑产品**。颜色按 `rgb()` 解析但浏览器给的是 `oklch()`、
   主题过渡动画的中间态、嵌套弹窗的层级判断 —— 这几次「假失败」最后都出在测量方式上。
5. **数据状态要进种子**。只测「健康状态」的数据会让一大批界面元素永远测不到
   (见下文「按数据状态」一节)。
6. **「写了」不等于「跑了」**。配置类的东西(全局闸门、中间件、代理)必须有一条**静态**检查,
   确认它在框架真正会加载的位置。`middleware.ts` 放在仓库根目录、而项目是 `src/app` 布局时,
   Next 会**静默忽略**它 —— 构建产物里一条都没编出来,而当时所有用例照样全绿。
   现在由 `verify-write-guards` 守着这一条。

## 一、纯函数单测(`npm run test:unit`)

| 模块 | 覆盖要点 |
| --- | --- |
| `validation` / 日期 | 两种合法写法、非法值与不存在的日期、时间点字段保留时刻;**「填过头」的字段都说得出是哪一项** —— 采购项名称(≤80 字)与数量、空间名称(≤30 字)、任务名称(≤80 字)与备注(≤500 字)越界后必须是中文消息(2026-11-28 实测:添加空间填 36 个字时,弹层里只有 `String must contain at most 30 character(s)`);外加一条**源码级守卫** —— 采购项弹层的提交必须有 `catch` **并且**把报错显示在弹层里(它此前两样都没有:填 85 个字点「加入清单」后界面一个字都没有、也没有提示条,原因只作为未捕获错误落在控制台;隔壁「添加家庭空间」弹层一直是对的) |

| `item-merge` / `item-metrics` / `item-sort` / `item-insight` | 合并计划、单位换算、排序、结论文字;`item-metrics` 另含 `scanConsumeBlocker` —— **扫码页能按件消耗的前提**(耐用品 / 液体各给各的理由,文案与服务端 409 的原话是同一条常量) |
| `household-report` / `space-summary` / `chart` / `spend-forecast` | 月报数字、空间摘要、图表聚合(月报与空间摘要里的「该补货」和概览同一口径:暂停补货中的物品不算);**「临期」也同一口径** —— 窗口由调用方传入(此前空间卡写死 7 天、月报写死 30 天,用户设置只在提醒中心生效),已过期单独计数、不并进临期,摘要文案把「已过期」与「临期」分开说;**统计范围也要同一个数** —— `spaceSummary` 收「自己 + 下级空间」的 id 集(此前只比 `item.locationId === id`,于是自己没物品、下级有物品的空间卡片写「还没放东西」,点进去却有东西);有下级空间时文案补一句「含 N 个下级空间」(否则「父 3 件 / 子 2 件」摆在同一屏像多数了一件);**已用完(0 件)的物品也不占件数** —— 它在任何列表里都看不到(物品页/搜索/空间筛选都按 `quantity > 0` 取,消耗到 0 件时提示条也会说「已从物品列表隐藏」),而卡片曾把它算进去:2026-11-28 探针库实测,一件物品在厨房里消耗到 0 件后,空间页写「厨房 3 件」、按空间筛选点进去只有 2 件(概览接口里那个没人读的 `_count` 也调成同口径);**「快用完了」是另一条口径** —— 用完的正是该补货的,概览与月报都特意带上它,不在这条规则里;同一条规则写在**两处**(`spaceSummary` 的统计范围、空间页导轨的 `countIn`),漏一处就会冒出两个数 —— 导轨那处此前也没过滤,已一起补上,并加了一条**源码级守卫**:断言 `countIn` 里必须有 `item.quantity > 0`;**删空间前的提示也不许许诺做不到的事** —— 里面只剩「已用完」(数量 0 件)的物品时,提示语要说「其中 N 件已经用完、不显示在物品页和搜索里,现在没有入口移动或删除它们,所以这个空间暂时删不掉」,而不是「请先移动」(2026-11-28 探针库实测:导轨与卡片都写 0 件 / 「还没放东西」,删除却回「还有 1 件物品,而那件东西在物品页、搜索、回收站里都找不到;服务端 409 同口径补上「其中 N 件已经用完、不在物品列表里」);调用方少传这个数会由源码级守卫挡下 |
| `category-share` | 「前 N 类 + 其余合并成『其他』」的合并规则,**一条都不能少** —— 概览「本月花在哪」与月报此前各写一遍「把数组砍到前 4 条」,尾部类别整个丢掉,而占比图表的百分比只按**传进去的那几行**算,于是同一个面板里两个必须相等的数字对不上:「本月 ¥10370」vs 四行之和 ¥10332,百分比还照样是 58+26+11+5 = 100%,被丢掉的「饮品 ¥37.5」在界面上毫无痕迹(2026-11-28 探针库实测);同页的「库存分布」早就合并出「其他」,这条把规则抽成一处并补了一条**源码级守卫** —— 概览接口、月报、库存分布三处都必须经过 `topWithOtherRows`,两个金额面板里不许再出现「砍到 4 条」的老写法,「其他」也不许变成可点的筛选项 |
| `consumption-ranking` | 「最近用得多」的合并规则(概览首屏的排行条与「查看消费详情」里的前 3 名共用这一份数据):流水的 `itemName` 是**记录那一刻**的名字快照(留旧名是为了让历史说得清),可榜单问的是「这件东西用得多」—— 按名字聚合会把同一件物品改名前后算成两件;**2026-11-28 探针库实测**:同一件物品 6 次消耗(改名 A 前 3 次 + 改名 B 后 3 次)在榜上是两行各 3 次,真第一名被只消耗 4 次的物品压在下面,而且两行占掉 top-5 的两个名额、把本该上榜的挤了出去(改名后只再消耗 1 次时更直接:两行各 1 次,连榜都上不去)。现在按 `itemId` 归并、显示名以**库存里的当前名字**为准(改名后即使还没再消耗,榜上也不会出现一个库存里根本不存在的名字)、id 已查不到的旧流水退回按名字聚合;两件真的同名的物品合成一行。其中一条用例**只有按 id 归并才过**:物品甲改名后旧名字被物品乙用了,按名字归并会把甲改名前的次数并进乙那行 |
| `item-visibility` | 「看得见的物品」这条规则的地基:**筛选条件与数量分开** —— 两者混在一起时,`quantity > 0` 那条会把**已用完(0 件)**的物品挡在所有列表之外(这是有意的,消耗到 0 件时提示条也会说「已从物品列表隐藏」),可它们因此**在界面上完全没有入口**(不在物品页、不在搜索、不在回收站):2026-11-28 探针库实测,空间卡片写「还没放东西」、删除却回「还有 1 件物品,请先移动」,而那件东西根本找不到,补货也无从下手。现在 `pickVisibleItems(items, conditions, "live" \| "usedUp")` 让「已用完」也有入口,而两份列表**用的是同一套筛选条件**(搜索字段那次的教训:一处定义,别各写一套);原有的源码级守卫同步更新为「两个入口任选其一都算过」,并**新增一条断言**:`lib/item-visibility` 必须经过 `matchesSearch` |
| `csv-import` / `item-type-guess` / `fridge` / `task-recurrence` | 导入解析、类型猜测、**冰箱清单**(位置名判定、「开封后冷藏」只提醒不算没放好、**用完的不再提醒放回去**、「算了就必须交出去」的契约)、重复任务的下一次到期 |
| `shopping-list` | **「在不在采购清单里」的判定**:名字归一 + **单位**一起比 —— 与服务端合并采购项用的是同一把键(只看名字,界面就会说「这件不在清单里」,而点下去其实被合并、数量翻倍);已购买的不算「还在清单里」;**常买且买过的那几条**交给界面(★ 的提示语说「已加入常买清单」,就得真有那一栏) |
| `password` / `validation`(账号) | 密码强度各档、用户名规则 |
| `location-path` / `location-tree` | 空间路径的拼接,以及**环检测**(把孙子的上级设成上级会造出绕不完的环)+ **子树求法**(含孙辈;库里有环也不打转)—— 空间卡的件数、物品页的空间筛选都用它 |
| `local-date` / `weekly-review` / `relative-time` | 本地日历日、每周盘点设定日、相对时间文案 |
| `interactive-nesting` | 「行里的 trailing 是不是控件」的判定(判断错了就会渲染出 `<button>` 套 `<button>`) |
| `ai-error` | 上游 AI 报错的解读:各状态码与两种「图片链接被拒」措辞、HTML 去标签、超长截断;外加一条源码级守卫 —— 四个 AI 路由里不许再自己拼失败文案 |
| `script-probe-account-guard` | **建探针账号的闸门:默认只认探针库**。2026-11-28 只读实测:家庭库 `data/home-inventory.db` 里躺着 `leadcheck`(ADMIN)/`viewcheck`/`rcvlead` 三个账号(2026-11-20 19:01 建的,用户从没建过),用 scrypt 对着库里的 `passwordHash` 复核 —— **三个口令都能登录**,而口令就明文写在 `scripts/make-probe-accounts.mjs` 里:谁读到这个仓库、又能连上家里那台机器,就能以管理员身份进这个家。脚本原先对 `DATABASE_URL` 指向谁毫无判断,指到哪个库就 upsert 到哪个库。现在默认只认探针库(`probe` / `ci` / `empty` / `test` / `hygiene`),别的一律拒绝;CI 的 MySQL 作业(库名 `homeinventory` 看不出是探针库)显式写 `ALLOW_PROBE_ACCOUNTS=1` —— 那是一个看得见的动作,而不是一次疏忽。拒绝信息里还会先把连接串的**口令抹掉**再打印(它会进 CI 日志) |
| `auto-backup-schedule` | **「今天该不该自动备份」的判定**:只有成功才算今天做完了;失败之后还能再试(30 分钟冷却),但不会每次翻页都弹提示;失败发生在昨天不拖住新的一天;失败时刻在「未来」(时钟被改过)不许把今天永久卡死;标记格式兼容旧版、坏数据当没记录。由来:客户端把标记写在判断 `response.ok` 之前,一次 500 就让这一天再也不会重试 |
| `backup-files` / `backup-label` | **每日自动备份该写哪个文件名,以及下拉里怎么把它说明白**。实测家庭库 2026-11-28 那份被同一台机器上的探针实例顶掉(9 件物品 → 探针库的 15 件「界面检查·…」),文件名一模一样、里面也没有任何「哪个库写的」的痕迹。现在:空位用朴素名;今天这份本来就是本库写的仍用朴素名;是**别人的**(老文件没有 `database` 字段、读不动,一律算「不是本库的」)→ 带本库指纹另存,**绝不覆盖**。附带钉住指纹形状(`DATABASE_URL` 的 sha256 前 6 位,不是原串)、名字合法性(含路径穿越)与分组(多实例各留各的保留份数) |
| 一致性 | 服务端写入的动作都有中文标签;代码引用的 `/api` 路径都有对应路由 |
| 写接口守卫 | 每个非 GET 处理器必须有权限校验,或在「设计上公开 / 自带细粒度校验」清单里(清单同时校验不过期) |
| 配置文档一致性 | 代码用到的用户可配置环境变量都必须在 README / compose 里出现;开发专用白名单同时校验不过期 |
| CI 工作流自检 | 每个步骤有 run/uses、引用的脚本存在、关键作业与检查仍在(工作流无效时 CI 根本不会跑,所以这条放在本地 test:unit 最前) |
| 两份 schema 同步 | MySQL 用的 `schema.mysql.prisma` 必须与 `schema.prisma` 的表/字段完全一致(容器启动时会用它覆盖正式 schema) |

## 四、发布前

镜像构建流程里带一次**运行时冒烟**:容器起来后完成
「健康检查(且镜像自报的版本 == 检出/打标签的版本)→ 初始化管理员 → 登录 → 建物品 → 读回」,
两个架构各跑一次(arm64 在原生 runner 上单独再跑一次)。

版本那一条是 v0.1.127 补的:发布产物必须能自证版本 —— 本地就发生过「界面显示 0.1.125、
`package.json` 已是 0.1.126」(先构建、后改版本号)而界面上看不出异常的情况。
CI 每次都是"先改版本号再构建",所以这类错 CI 天生看不见,只能由产物自己回答。

## 五、按数据状态看覆盖

界面检查能测到什么,取决于**库里有什么数据**。CI 的种子数据(`scripts/seed-ci-fixtures.mjs`)
专门覆盖「只有特定状态才会出现」的元素:

| 状态 | 种子数据里有什么 | 影响哪些界面元素 |
| --- | --- | --- |
| 已过期 | 3 天前到期的酸奶 | 红色到期徽标、概览红点、提醒中心过期分组 |
| 即将到期 | 5 天后到期的鲜奶 | 提醒中心临期行 |
| 低库存 | 最小库存 5 / 数量 1 | 该补货角标、补货建议 |
| 余量见底 | 清洁瓶装 8% | 液体余量徽标 |
| 已经用完 | 数量 0 + 日均消耗 1 的挂面 | 「快用完了」里「已经用完了」那一行(概览与月报必须都列) |
| 暂停补货 | 日均消耗 1 + 暂停到 7 天后 | 「快用完了」里**不该**出现的行(概览、月报、AI 上下文三处) |
| 已经喝完的冷藏品 | 数量 0 + 需冷藏 | 冰箱清单里**不该**出现的行(月报会念它「还没放好」) |
| 开封后冷藏 | 需冷藏但要开封后才算 | 概览「冰箱清单」的那一行(件数里算它,就得列出来) |
| AI 结论过时 | 带 `aiSummary` + 旧 `AI_ANALYZE` 记录 | 列表「建议重新分析」胶囊 |
| 回收站有东西 | 一件已软删 | 回收站弹窗的行 |
| 采购 / 任务非空 | 一条待采购、一条任务 | 两个视图的行 |
| 已经在采购清单里 | 一条采购项与一件**同名同单位**的低库存物品 | 首屏「最需要做的事」**不许**再给「加入采购清单」(要说「清单里已经有一份」+「查看采购清单」),而**同一个名字但单位不同**的那件仍要正常给加入入口(单位是键的一部分) |
| 买过的常买项 | 一条「已购买 + 已标常买」的采购项 | 物品页采购清单里的「常买」一栏(此前只提示「已加入常买清单」,界面上没有任何地方看得见它) |

上面最后两行**不在种子里**,由套件自己现造(`verify-shopping-list-ui`):这两个状态必须量在
**空库**上 —— 首屏挑哪一件事由数据决定,种子里的过期 / 临期 / 低库存物品会把它抢走。
种子里放一份「已经在清单里」的物品,只会让别的作业看到几个元素,却让这条断言永远量不到探针;
需要种子覆盖的,是那些**只看渲染、不看首屏抉择**的元素。

**空间层级也是套件自建的**:「自己 0 件、下级有 1 件」这种形状放进种子会很别扭(种子是平铺的),
所以 `verify-space-counts-ui` 自己建一棵三层的树、量完删净。它不要求空库,但要求能写。

> 这张表是**补出来的**:此前种子里只有健康状态的物品,上面这些元素在 CI 里从未被对比度、
> 窄屏、无障碍检查看到。补上之后第一次运行就抓到「建议重新分析」在深色下对比度只有 2.03。

> 并发也算一种「数据状态」:同一份数据被多个写者同时改。相关检查见 `verify-concurrency`。

> 另外:`/consume/[id]` 是**无需登录**的写入口(扫码即消耗一件),
> 它的幂等与液体分支由 `verify-consume-scan` 覆盖。

## 六、已知未覆盖(诚实清单)

| 方向 | 为什么没做 |
| --- | --- |
| 首屏渲染时间(LCP/TTI) | 机器相关,进 CI 只会产生假失败;体积预算与相对耗时阈值已覆盖可稳定比较的部分 |
| 对象存储(OSS)上传 | 需要真实 OSS 配置;而**默认的本地存储路径**已由 `verify-image-upload` 覆盖(上传→落盘→读回→删除清理) |
| AI 相关功能 | 需要 API Key(gated by `aiAvailable`);套件在未配置时打印跳过原因而不是伪装通过 |
| 相机 / 屏幕共享扫码 | 需要真实摄像头与屏幕共享权限;但**解码链路**已由 `verify-qr-scan` 覆盖(用应用自己生成的二维码走「图片」模式) |
| 纸上的最终结果 | 排版几何(尺寸/边界/换行)已用 print 媒体验过,但真实打印机的输出无法在 CI 里验证 |
| 两个标签页同时操作 | v0.1.30 手工探针确认行为正确:一处删掉、另一处正在编辑并保存时会明确报「找不到这条记录,可能已被删除」,且不关掉弹窗把用户的改动丢掉。但**没有**写成回归:驱动「另一处删除」需要在同一 context 开第二个标签页并在恰当时机操作,叠上自动弹层后不稳定 |
| **登录限流的三层与取舍** | 三层都**只统计失败**的尝试:来源(取 XFF **最右**值)12 次/分钟、账号 10 次/分钟、全局 120 次/10 分钟;成功登录不计数,并会清掉该账号的失败计数。实测:只按来源限流时,每个请求换一个 X-Forwarded-For 就能**无限猜**(连续 15 次 0 次被拦);改成三层后,换着来源打同一账号第 11 次被拦、来源与用户名一起换也要轮换到一定次数才被全局层拦下。取舍:持续攻击期间所有人登录会慢一拍(计数在进程内存,重启即清空;多副本各算各的) |
| **上传目录的读取边界** | 实测(7 种穿越变形都试过):未登录 401;`../../`、`..%2f`、`%2e%2e%2f`、`..%5c`、`....//` 等全部 404;上传目录里非白名单后缀 404;响应带 `nosniff`。**同一家庭内任意登录账号都能读图片**(成员/只读也一样)——这是家庭共享模型的设计,文件名是 UUID、不可猜;如果将来要做「按账号隔离相册」,这里需要改 |
| 请求发不出去(断网 / 接口失败) | 手工探针确认会提示「网络响应不完整,请重试;已保存的内容不会丢失」且服务端数据不变;但没能做成稳定可复现的自动检查(Playwright route abort 在有 Service Worker 时不生效,屏蔽 SW 后又常被自动弹层遮挡;「用掉」路径先弹应用内确认框、请求时机不稳)。按「做不稳的检查不写进去」的原则留空 |
| 空间卡片的右键菜单(自动化) | 删空间这条路径的唯一入口是卡片右键菜单;实测 Playwright 右键、按坐标右键、直接派发 contextmenu 都打不开菜单(三次),所以「删空间」的**界面级**断言没有写成回归。文案逻辑已抽成纯函数 `spaceDeletePrompt`,由 `scripts/unit/space-delete-prompt.test.mjs` 覆盖 |
| 打印工作室的自动扫描 | 它是嵌套弹窗,自动判定不稳定,所以没有纳入**弹窗扫描**(在 `verify-modals-a11y` 里写明了原因)。但它的**内容**已有覆盖:v0.1.29 起 `verify-print-layout` 会自建一件 49 字的探针物品,量标签上的名字是否真的显示两行、超出行钳、二维码是否够扫、编号是否印出来 |

### 跑套件请用临时库(实测代价)

**任何套件只要走真实接口就一定会写「活动记录」** —— 实测每类操作(建物品 / 改 / 消耗 / 撤销 /
加采购 / 建空间)恰好各写 1 条。所以:

```bash
# 临时库 + 另一个端口,别对着家里的真实库跑
DATABASE_URL="file:../data/scratch.db" npx prisma db push --schema prisma/schema.prisma --skip-generate
DATABASE_URL="file:../data/scratch.db" PORT=3002 npm start
BASE_URL=http://127.0.0.1:3002 PROBE_USER=... PROBE_PASS=... node scripts/verify-xxx.mjs
```

`verify-suite-hygiene` 会把本次新增的活动记录条数**打印出来**(只报告、不判失败),
免得再出现「连跑几轮,真实库里攒了 7.3 万条流水(约 29 MB)」那种事。

顺带记两个实测数字(用于判断要不要保留策略):
**家庭日常按每天 20 次操作,一年约 7,300 条 ≈ 2.9 MB,十年 ≈ 29 MB** ——
所以**没有**给活动记录加自动清理;而且 SQLite 删除后文件不会自己变小(要 `VACUUM`)。
